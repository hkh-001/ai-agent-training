## 2. 一分钟地图

### 2.1 数据流

```
【内部世界】Python 对象                    【边界】wire dict              【外部】模型
ChatMessage(role="user",                 {"role":"user",
            content="A1 还有货吗")  ──to_wire──▶ "content":"A1 还有货吗"}
                                                        │
                                                        ▼  (SDK 负责 json.dumps)
                                    {"tool_calls":[{"id":"call_7",
                                      "function":{"name":"get_stock",
                                                  "arguments":"{\"sku\":\"A1\"}"}}]}
                                                        │
ToolCall(id="call_7",                                   │
         name="get_stock",        ◀──from_wire──────────┘   ← 把字符串解析成 dict
         arguments={"sku":"A1"})                             （解析失败必须报错，不能猜）
              │
              │ 宿主执行工具（模型没有执行权）
              ▼
ChatMessage(role="tool", tool_call_id="call_7", content='{"available":3}')
                                          ↑ 必须原样回填模型给的那个 id
```

### 2.2 四种 role 的所有权

| role | 谁写的 | 模型会输出它吗 | 存在哪 |
|---|---|---|---|
| `system` | 开发者 | ❌ | 你的代码 |
| `user` | 终端用户（经你转发） | ❌ | 你的代码 |
| `assistant` | **模型** | ✅ **唯一出口** | 模型产出 → 你存下来 |
| `tool` | **你的程序**（工具结果） | ❌ | 你的代码 |

**四个入口，一个出口。** 这四个 role 全部都是"你发给模型"的，区别只在**署名**。

## 3. 核心概念（按理解顺序）

### 3.1 模型是失忆的：历史由你保管

> **结论**：模型没有记忆。每轮请求，你都要把**整份历史**重发一次。

```
第 1 次请求：[system, user]                      → 模型输出 assistant(tool_calls)
第 2 次请求：[system, user, assistant, tool]     → 模型输出 assistant(content)
第 3 次请求：[system, user, assistant, tool, assistant, user] → ...
```

所谓"模型记得自己刚才说过什么"，真相是：**你又把那条 assistant 消息发了一遍**。

**推论**：
- "记忆"策略 = "重发什么"策略 → 这是 M2 的主题；
- 成本随轮次 **O(n²)** 增长（每轮都为全部历史付费）；
- 上下文窗口是硬上限，超了就是 400 或静默截断。

**反例（常见误解）**："模型自己会记住上一轮" → 不会。你不发，它不知道。

---

### 3.2 四种 role 是"署名"，不是"发送者"

> **结论**：你永远是唯一的递交者；`role` 只是材料上的署名。

一次 HTTP 请求里可以同时出现四种 role：

```json
{"messages": [
  {"role": "system",    "content": "你是电商客服…"},
  {"role": "user",      "content": "A1 还有货吗？"},
  {"role": "assistant", "tool_calls": [...]},
  {"role": "tool",      "tool_call_id": "call_1", "content": "{\"available\":5}"}
]}
```

**这四个都是你的程序一次性提交上去的。** 里面有 system/user/assistant/tool 四种署名，递交者只有一个：你。

**类比：会议记录员。** 老板（模型）每次开会都失忆，所以每次你都要重新递一份完整记录。记录里每段话标注"谁说的"，但递交的人始终是你。

> 秘书不会因为代笔一封"以 CEO 名义"的信，就变成 CEO。
> 你也不会因为追加了一条署名 `tool` 的消息，就变成工具。

**所以正确说法**：
- ✅ "我追加一条 tool 消息" / "我把工具结果以 tool 署名写进请求"
- ❌ "我发一条 user 消息"（容易误以为发送者 = 用户）

---

### 3.3 三层表示：对象 / dict / JSON 文本

> **结论**：不是"哪些消息用 dict、哪些用 JSON"，而是**同一条消息在不同层有不同表示**。

| 层 | 形态 | 例子 | 谁负责转换 |
|---|---|---|---|
| L1 | Python 对象 | `ChatMessage(role="user", content="hi")` | 你 |
| L2 | Python dict | `{"role": "user", "content": "hi"}` | `to_wire()` |
| L3 | JSON 文本 | `'{"role": "user", "content": "hi"}'` | SDK / `json.dumps` |

**判断标准：带不带引号。** 有引号 = 字符串（JSON 文本）；没引号 = dict。

#### 特殊字段：`arguments`（唯一的"提前降级"）

| 层 | `arguments` 的形态 |
|---|---|
| L1 对象 | `{"sku": "A1"}` ← **dict** |
| L2 dict | `'{"sku":"A1"}'` ← **JSON 字符串**（协议强制） |
| L3 文本 | `"{\"arguments\": \"{\\\"sku\\\": \\\"A1\\\"}\"}"` ← 双重转义 |

`function.arguments` 在 OpenAI 协议里**类型是 string**，所以它必须提前一步变成字符串，形成"字符串套在 dict 里"的双重编码。

#### 你日常只写到 L2

```python
client.chat.completions.create(
    model="deepseek-chat",
    messages=[{"role": "user", "content": "hi"}],   # 传 dict，SDK 内部 dumps
)
```

L3 由 SDK 负责。**你永远不需要手写 L3**，除非落盘 trajectory 或抓包调试。

---

### 3.4 `ToolCall` 是模型的"点菜单"，执行权在宿主

> **结论：模型是嘴，你是手。**

```
模型能做的：说"我要查 A1 的库存"       ← 输出 ToolCall
模型不能做的：真的去查数据库             ← 没有网络、没有文件系统、没有你的权限
```

**三个工程后果**：

1. **安全边界在你手里**：模型说"删掉所有订单"，是你的 dispatcher 决定拒不拒绝；
2. **错误处理在你手里**：工具失败/超时/参数非法，都要变成 tool 消息回给模型（模型看不见异常）；
3. **权限在你手里**：菜单是你给的（`tools=[...]` 里没写的工具，模型调不了）。

**餐厅类比**：

| 环节 | 谁 |
|---|---|
| 客人说"来份牛排" | 模型输出 `ToolCall` |
| 服务员记单、送后厨 | 你的 dispatcher |
| 后厨做好 | 工具函数（返回 dict） |
| 服务员端上桌："3 号单，牛排" | **你的 `tool_result()`** |
| 客人说"再来杯咖啡" | 模型下一次输出 |

---

### 3.5 `tool` 消息 = 工具结果的回填，靠 id 配对

> **结论**：`tool` 消息是"你告诉模型：你刚才让我做的事，结果是这样"。

三个精确点：

**① id 必须一模一样**

```python
assistant(tool_calls=[ToolCall(id="call_1", name="get_stock", arguments={"sku": "A1"})])
tool_result("call_1", '{"available": 5}')      # ← 同一个 id
```

历史里可以有多组配对（多轮工具调用），模型靠 id 区分"哪条结果对应哪次请求"。

**② `assistant(tool_calls)` + `tool` 是原子对**

| 状态 | 后果 |
|---|---|
| 有 assistant(tool_calls)，没有对应 tool | 400：`must be followed by tool messages` |
| 有 tool，前面没有对应 assistant(tool_calls) | 400：孤儿 tool 消息 |
| id 对不上 | 400，或更糟：结果错配 |

**③ 一次调用 → 一条 tool 消息（1:1）**

模型一轮返回 3 个 `tool_calls`，你要回 3 条 `tool` 消息。不能"合并成一条综合结果"。

**历史生长示例**：

```
[system]      你是电商客服…
[user]        A1 还有货吗？帮我留 2 件
[assistant]   tool_calls: call_1 → get_stock("A1")
[tool]        call_1 → {"available": 5}          ← 第 1 对
[assistant]   tool_calls: call_2 → reserve("A1", 2)
[tool]        call_2 → {"ok": true, "left": 3}   ← 第 2 对
[assistant]   "A1 现可售 3 件，已为你预留 2 件"      ← 终点（无 tool_calls）
```

#### `tool` 消息 ≠ 日志

| | `tool` 消息 | 日志（M6） |
|---|---|---|
| 给谁看 | **模型** | 人 / 监控 |
| 必须配对 | **是**，id 严格对应 | 不需要 |
| 缺了会怎样 | 请求 400 | 只是排查少线索 |
| 会被发出去吗 | **会，且每轮重发** | 不会 |

所以 **给程序员的堆栈不能塞进 tool 消息**：`KeyError: 'stock'` 模型看不懂还浪费 token。要给模型看的是：`{"error": "库存不足，当前可用 5 件"}`。

---

### 3.6 为什么消息要不可变（`frozen=True`）

> **结论**：消息会被**记录、回放、断言**，可变对象会让这些操作互相污染。

```python
mock.calls.append(call)          # 记下了
history[0].content = "改一下"    # 你以为只改了历史
assert mock.calls[0].messages[0].content == "你好"   # 💥 记录也变了
```

你之后要做的 trajectory 落盘、RL 回放，全靠"消息不可变"这个前提。

**注意**：`frozen=True` 只保证"字段不能重新赋值"，**不保证字段内部的容器不可变**。所以：
- `ChatMessage`、`ToolCall` 是 frozen → 浅拷贝安全；
- `tools` 里的 schema 是普通 dict → **必须 deepcopy**（见 §6 第 3 条）。

## 4. 你的 12 个疑问（原话 + 解答）

### Q1「m1 是要在哪个文件上写代码」

`bootcamp/common/types.py`（4 个 TODO）+ `bootcamp/common/llm.py`（1 个 TODO）。测试文件不要动。

### Q2「tool 分支允许空，是不是可能不调用 tool？」

**不是，因果关系相反。**

- "工具有没有被调用" → 由**有没有这条 tool 消息**决定；
- "调用的是哪一次" → 由 `tool_call_id` 决定；
- "`content` 是什么" → 只是"这次调用返回了什么"的**文本**。

`role="tool"` 这条消息存在的唯一理由，就是"某个工具已经被调用过了"。

为什么文本可为空：工具可能成功但没有可说的内容（"标记已读"）。所以规则是：**结果本身可以为空，但这条消息必须存在、id 必须对得上**。

一句话：**tool 的空 content = "做了，但没话说"；user 的空 content = "没说，那你要我干什么？"**

### Q3「user 分支的 content 是不是用户要问的问题，所以不为空」

**对。** 更准确说：`user` 消息 = "这一轮驱动的输入"，可以是提问、指令、确认，但都必须有内容。

两个细节：

- **为什么用 `strip()`**：`"   "` 是 truthy 但语义为空。不 strip 就会让模型回一句"你想问什么？"——**bug 变成语义问题，比报错难查十倍**；
- **为什么在边界拦**：空输入、变量拼错都会产生空 content。在边界报明确错误，比让它流进模型再回头猜便宜得多。

### Q4「为什么末尾都要有 return，这个我不懂」

因为**函数体是从上往下顺序执行的，`if` 只决定"这段要不要执行"，不会让后面自动跳过**。

30 秒实验：

```python
def check(role, tool_call_id):
    if role == "tool":
        print("① 通过了 tool 分支")
        # return          ← 注释掉
    if role == "assistant":
        print("② 通过了 assistant 分支")
    if tool_call_id is not None:
        print("③ 被最后一段误伤 → raise")

check("tool", "call_1")
# 输出：① ③   ← 合法的 tool 消息被 system/user 的规则误伤
```

**这就是"早期返回（early return）"模式**：每条分支处理完自己那类，`return` 交差。

这里的 `return` 不返回任何值（`-> None`），作用**仅仅是"结束函数"**。

### Q5「seen 这个语法我也不懂」

```python
seen: set[str] = set()      # ① 造空集合（空的"已见过名单"）
if call.id in seen:         # ② 查名单：见过吗？
    raise ValueError(...)
seen.add(call.id)           # ③ 没见过 → 记进名单
```

`set` vs `list`：

| 操作 | `list` | `set` |
|---|---|---|
| 判断"在不在" | 挨个看，O(n) | 哈希直跳，O(1) |
| 能否重复 | 能 | 不能（自动去重） |

为什么必须去重：`tool_call_id` 是回填结果的**唯一锚点**。两个 id 相同 → 无法确定哪条结果对应哪次调用 → 把价格当库存返回 → **模型会基于错误事实"合理地"继续编下去**，错误隐蔽且致命。

### Q6「raise 是什么语法」

> `raise` = **主动中断当前函数，把一个错误对象扔给调用者**。

| | `print("库存不足")` | `raise ValueError("库存不足")` |
|---|---|---|
| 告诉谁 | 屏幕前的人 | **调用这个函数的上层代码** |
| 程序继续吗 | 继续 | **立刻中断**，一路往外抛 |

三种写法：

```python
raise ValueError("库存不足")     # ① 最常用
raise ValueError                # ② 只给类，消息为空（不推荐）
raise                           # ③ 只能在 except 里：把当前异常原样再抛
```

异常会**冒泡**：`validate()` 抛 → `to_wire()` 崩 → `main()` 崩，除非中途有人 `try/except` 接住。`pytest.raises` 就是帮你"接住并断言"的工具。

**配套的 `try/except`**：

```python
try:
    args = json.loads(raw_args)
except json.JSONDecodeError as exc:
    ...
```

- 只接你预期的那一类（`except Exception` 会把你自己代码的 bug 也吞掉）；
- `as exc` 拿到异常对象（`exc.msg`/`exc.pos` 是诊断信息）；
- **接住之后必须做点什么**，最糟的是 `except: pass`。

### Q7「问题 1（`or []`）我还是没有懂」

`.get()` 有**两种情况**返回 `None`：

```python
{}                         .get("tool_calls")   # → None   ① 键不存在
{"tool_calls": None}       .get("tool_calls")   # → None   ② 键存在，值是 null（真实 API 会这样）
```

而 `None` 不能被 `for` 遍历：`TypeError: 'NoneType' object is not iterable`。

⚠️ **关键坑**：`get(k, [])` 的默认值**只在情况 ① 生效**：

| 情况 | `get(k)` | `get(k, [])` | `get(k) or []` |
|---|---|---|---|
| ① 键不存在 | `None` | `[]` | `[]` |
| ② 值是 null | `None` | **`None`** 💥 | `[]` ✅ |
| ③ 值是 `[]` | `[]` | `[]` | `[]` |
| ④ 有值 | `[c1,c2]` | `[c1,c2]` | `[c1,c2]` |

**`or` 的真相**（很多人卡在这）：`a or b` **返回操作数之一，不是布尔值**。

```python
None or []          # → []          None 是 falsy，返回右边
["c1"] or []        # → ["c1"]      非空列表是 truthy，返回左边
```

falsy 清单：`None`、`[]`、`{}`、`""`、`0`、`0.0`。

**口诀：`get` 的默认值防"没这个键"，`or` 才防"值是空的"。**

### Q8「所以 to_wire 和 from_wire 有什么区别」

**方向相反：`to_wire` 是出口，`from_wire` 是入口。**

| | `to_wire()` | `from_wire()` |
|---|---|---|
| 方向 | 对象 → dict（**出**） | dict → 对象（**进**） |
| 时机 | 发请求**前** | 收到响应**后** |
| JSON | `json.dumps` | `json.loads` |
| 失败概率 | 低（对象已校验） | **高**（外部数据不可信） |
| 方法类型 | 普通方法 `self` | **类方法 `cls`** |

**为什么一个是 `self` 一个是 `cls`**：

```python
msg.to_wire()                 # 已有对象，让它交出 wire 形态
ChatMessage.from_wire(data)   # 只有 dict，需要凭它"造"一个新对象 → 工厂方法
```

用 `cls(...)` 而非写死 `ChatMessage(...)`，子类继承时能自动返回子类实例。

**它俩必须互逆**：`from_wire(msg.to_wire()) == msg`（roundtrip 测试）。

`wire` 这个名字 = "线" = 数据在网络上传输时的格式（像"报关单"）。

### Q9「什么时候调用 to_wire，什么时候调用 from_wire」

**整个 Agent 循环里只有两个调用点**：

```python
def call_model(client, messages, tools) -> ChatMessage:
    payload = [m.to_wire() for m in messages]        # ← ① 出口
    resp = client.chat.completions.create(..., messages=payload, tools=tools)
    return ChatMessage.from_wire(resp.choices[0].message.model_dump())   # ← ② 入口
```

三个额外场景：

| 场景 | 用哪个 |
|---|---|
| 落盘轨迹（trajectory.jsonl） | `to_wire` |
| 回放轨迹 / 读测试数据 | `from_wire` |
| 单元测试 | 两个都用（roundtrip + 断言 wire 格式） |

**不要在这些地方调**：程序内部传递时（一旦变 dict 就失去 validate 和属性访问）、`from_wire` 后又 `dumps`（双重编码）。

### Q10「m1 部分就是 call_model 的实现吗」

**不是。** M1 是"数据的形状 + 边界的翻译"，**没有一行代码真正联网**。

| 层 | 模块 | 负责什么 | 典型 bug 症状 |
|---|---|---|---|
| 数据层 | M1 `types.py` | 消息长什么样、合法吗 | `KeyError` / `TypeError` / 400 |
| 边界层 | M1 `to_wire/from_wire` | 怎么进出、怎么翻译 | `arguments` 是字符串、双重编码 |
| 策略层 | M2 `context.py` | **该发哪些**消息 | token 超限、模型"忘了"前文 |
| 控制层 | M5 `loop.py` | 什么时候停 | 死循环 |
| 工程层 | M6 `harness/` | 记录/重试/成本 | 无法复现 |

`call_model` 只做三件事：**拼装（用 M1 的 to_wire）→ 发 → 解析（用 M1 的 from_wire）**。

**为什么不用 `call_model` 当 M1**：可测试性。M1 的 21 个测试**不需要 API Key、不需要网络、结果确定**。这是"能在离线状态把核心逻辑测透"的能力，也是 M6/M12 的地基。

### Q11「tool 可以理解为之前调用的 tool 得到的结果加进历史吗」

**对。** 补三个精确点：

1. 不是"之前随便哪次"，而是**刚刚那一次、用 id 绑定**；
2. `assistant(tool_calls)` + `tool` 是**原子对**，不能只有一半；
3. 一次调用 → 一条 tool 消息（1:1），不能合并。

它是**历史的一部分**，之后每轮都要重发（除非被裁剪）。

### Q12「什么叫'我主动发送一条 tool 消息'，我发的消息难道不应该是 user 吗」

**混淆了"发送者"和"署名"。**

- **发送者**：永远是你的程序（一次请求只发一个 HTTP 请求）；
- **署名（role）**：这段内容"以谁的身份"出现在对话里。

一次请求里有 4 种署名，但**递交者只有一个**。你不会因为追加了署名 `tool` 的消息就变成工具。

**工具结果为什么不能用 user 署名**（三个后果）：

1. **协议层 400**：每个 `ToolCall` 必须有 `tool` 消息回应；
2. **语义混淆**：模型对 role 有强先验——`user` 是"需求"，`tool` 是"事实"。把库存写进 user，模型会以为"用户在告诉我库存"，从此不再调工具（**提示注入的温床**）；
3. **训练数据污染**：`role` 决定 loss mask，错标会教模型"复述用户给的假数据"。

## 8. 面试答题卡（考前 30 秒）

### Q1 `arguments` 为什么必须是字符串？

> 因为它是**模型生成的文本**，不是宿主传入的结构。模型只吐 token，且流式输出需要增量拼接，所以协议把它定义为 string；解析与校验由宿主兜底。

- 责任划分：模型"尽量写合法"，宿主"必须兜底"（转成 tool 错误让模型改写 / 重试 / 降级）
- 加分：`JSONDecodeError` 是 `ValueError` 子类，统一按 `ValueError` 处理是安全的

### Q2 `content=None` vs `content=""`

> `None` = 这一轮没说话，只有动作；`""` = 说了但内容是空的。带 `tool_calls` 的 assistant 用前者。

- `""` 在部分实现会 400（`content must not be empty`）
- `None` + `tool_calls=()` 是非法消息（既没说话也没动作）

### Q3 `tool_call_id` 的两个作用

> 协议层是配对锚点（否则 400），语义层是结果归属（否则上错菜）。

- 协议层：每个 ToolCall 必须有对应 tool 消息；孤儿 tool 消息也 400
- 语义层：id 错配 → 把价格当库存 → 模型基于错误事实继续推理，**日志看起来完全正常**
- 追问预备：两个 id 相同怎么办 → **拒收**（validate 已要求唯一）

### Q4 为什么 `to_wire` 和 `from_wire` 都要校验？

> 两个门面对两批都不可信的数据；单一收口，避免每个入口各写一套。

| 门 | 数据来源 | 不校验的后果 |
|---|---|---|
| `from_wire` | API / 轨迹文件 / 别人传的 JSON | 脏数据一路污染到训练集 |
| `to_wire` | 你程序里手搓的对象 | 非法消息发出去，报错在服务端，离现场很远 |

- 加分：序列化/反序列化必须**对称**，否则轨迹"存下来再读回来"会悄悄变形

### Q5 浅拷贝为什么不够？

> 浅拷贝只保护"容器壳"，保护不了"容器里的可变元素"。

- `ChatMessage`/`ToolCall` frozen → 浅拷贝够
- `tools` 里的 schema dict 可变 → 必须 deepcopy
- 三种补法：`deepcopy` / 不可变结构（`MappingProxyType`）/ 存档式快照（`json.dumps` 存字符串）
- 加分：**Agent 工程特别强调不可变**，因为要记录、回放、并行
